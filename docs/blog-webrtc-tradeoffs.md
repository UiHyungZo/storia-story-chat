# WebRTC 음성 통화, 처음부터 완벽하게 짜지 않은 이유

*기술 블로그 초안 — PRD 7절 "포트폴리오 활용 방안" 참고. 실제 발행 전 다듬을 것.*

## 왜 이 글을 쓰는가

Storia는 캐릭터와 텍스트/음성으로 대화하는 개인 프로젝트다. 채용 공고들이 공통으로 요구하던
"WebRTC 기반 음성 통화 연동 경험"을 증명하는 게 이 기능의 목적이었다. 그런데 막상 설계를
시작하면서 든 생각은 이거였다 — *"WebRTC로 실시간 양방향 음성 대화"를 1인 개발로, 7주
안에, 처음부터 완성형으로 짜는 게 정말 맞는 선택일까?*

이 글은 그 질문에 "아니오"라고 답하고 나서 실제로 무슨 일이 있었는지에 대한 기록이다.
결론부터 말하면: 처음엔 WebRTC를 아예 안 쓰는 안(B안)과 WebRTC만 증명하는 최소 데모(C안)를
분리해서 리스크를 낮췄고, 그러다 개발 중간에 생각보다 쉬운 절충안을 발견해서 계획을
뒤집었다. 그리고 그렇게 뒤집은 뒤에도 여전히 안 만든 부분이 남아있다. 그 남겨둔 부분이야말로
이 글에서 제일 하고 싶은 이야기다.

## 처음 계획: 일부러 WebRTC를 메인 경로에서 뺐다

"WebRTC 기반 음성 통화"의 정석적인 구현(이하 A안)은 이렇다:

```
유저 마이크 → WebRTC → 서버가 실시간으로 오디오 수신
→ STT → LLM → TTS → 서버가 합성 음성을 다시 WebRTC로 실시간 전송 → 유저 스피커
```

문제는 이 파이프라인의 마지막 단계 — "서버가 합성한 오디오를 살아있는 WebRTC 세션에
실시간으로 다시 흘려보내기" — 가 난이도가 상당히 높다는 점이다. WebRTC는 원래 P2P
브라우저 간 통신을 위해 설계된 스택이라, "서버가 마치 참가자처럼 오디오를 publish하는"
시나리오는 클라이언트 SDK만으로는 잘 안 풀린다. 게다가 백엔드가 Spring Boot(JVM)라는
점도 걸림돌이었다 — 이 방향의 서버 사이드 작업은 보통 Python/Node의 LiveKit Agents SDK
같은 프레임워크로 처리하지, JVM 생태계에 표준 경로가 마땅치 않다.

1인 개발, 7주, 그리고 이 프로젝트 말고도 챙겨야 할 다른 기능이 훨씬 많다는 제약을 감안하면
"WebRTC 파이프라인이 안 풀려서 남은 4주를 여기 다 갈아넣는" 시나리오가 제일 무서웠다.
그래서 처음 세운 전략은 리스크를 분리하는 것이었다:

- **B안 (메인 기능)**: WebRTC를 아예 안 쓴다. 클라이언트가 로컬 STT로 음성을 텍스트로
  바꿔 서버에 보내고, 서버는 기존 텍스트 채팅 파이프라인 그대로 LLM을 호출한 뒤 TTS로
  합성한 오디오 URL을 돌려준다. 클라이언트는 그 URL을 그냥 재생한다. "음성 대화"라는
  *기능*은 완성되지만, 엄밀히는 WebRTC 연동이 아니다.
- **C안 (자격요건 증명용 최소 데모)**: B안과 완전히 분리된 화면에서, `react-native-webrtc`로
  Offer/Answer/ICE 교환까지 직접 짜는 1:1 P2P 오디오 스트리밍만 보여준다. LLM과 통합될
  필요도 없다. 이 데모 하나의 존재 이유는 오직 "WebRTC 시그널링을 실제로 짜본 코드"를
  남기는 것.

기능 완성도(B안)와 기술 증명(C안)을 분리해두면, 최악의 경우에도 — B안만 붙잡고 있다가
일정이 밀리는 최악의 시나리오에서도 — C안 데모 하나는 확실히 남길 수 있다는 게 이
전략의 핵심이었다.

## 그런데 개발 중간에 계획이 뒤집혔다

B안 파이프라인을 만들던 도중, "이 김에 WebRTC(A안)까지 가면 오히려 더 빠르지 않을까?"라는
질문이 나왔다. 곧바로 전체를 다시 설계하는 대신, 먼저 리서치 스파이크로 실현 가능성과
비용부터 확인했다. 그리고 발견한 절충안이 있었다 — **LiveKit**(오픈소스 WebRTC SFU,
Cloud 무료 티어 제공)의 **Track Egress**가 참가자의 오디오 트랙을 파일 저장 없이
**WebSocket으로 raw PCM을 직접 스트리밍**해주는 옵션을 갖고 있었다.

이게 왜 절충안이 되는지 풀어보면:

- 클라이언트 ↔ LiveKit 구간은 **진짜 WebRTC**다. 마이크 오디오 캡처, ICE 협상, DTLS-SRTP
  암호화, 트랙 publish — 전부 실제로 일어난다. "WebRTC 연동 경험"이라고 쓸 근거가 여기서
  생긴다.
- 서버(Spring Boot)는 WebRTC를 전혀 다루지 않는다. LiveKit이 트랙 오디오를 우리 백엔드의
  일반 WebSocket 엔드포인트로 스트리밍해주면, 그걸 그대로 B안에서 이미 만들어둔 배치
  STT → Gemini → TTS 파이프라인에 흘려보내면 끝이다.
- 별도 클라우드 스토리지도 필요 없다. Egress를 S3 같은 곳에 파일로 저장하는 대신
  WebSocket 직접 출력을 쓰면 되니까.

즉 "서버가 WebRTC 미디어를 직접 다루는" 제일 어려운 부분(JVM 생태계의 약점이 정확히
여기였다)을 LiveKit에 통째로 위임하면서도, 클라이언트 쪽에는 진짜 WebRTC가 남는
지점을 찾은 것이다. 이 절충 지점을 세션 중에 "축소판 A안"이라고 불렀다. 그리고 이
결과로 원래 있던 6주차 C안(수동 WebRTC 시그널링 데모)의 존재 이유 — "B안엔 WebRTC가
전혀 없다"는 공백 — 이 사라졌다. 그래서 C안은 재평가 끝에 별도 데모 없이, 코드 한
줄 추가 없이 문서 정리만으로 종료했다.

## 그래도 여전히 안 만든 부분: "완전한" A안

여기서 솔직해질 필요가 있다. 축소판 A안이 가져다준 건 "클라이언트가 실제 WebRTC로
서버까지 오디오를 보낸다"는 것이지, "서버가 실시간으로 응답 음성을 다시 들려준다"는
것은 아니다. 지금 구현은 여전히 턴제(turn-based)다:

```
말하기(WebRTC 업로드) → 끝내기 → 폴링 → 완성된 오디오 URL 받아서 재생
```

완전한 A안 — 서버가 합성한 TTS를 그 LiveKit 세션에 실시간으로 다시 publish해서
자연스러운 대화처럼 들리게 하는 것 — 은 여전히 범위 밖으로 남겨뒀다. 이유는 앞서
말한 그대로다: 그 부분은 보통 Python/Node의 LiveKit Agents SDK로 처리하는 영역이고,
지금 이 프로젝트의 백엔드는 Spring Boot(JVM)다. 시도하려면 두 갈래 길이 있다:

1. 실시간 미디어 publish가 가능한 JVM 라이브러리를 더 찾아본다 (지금까지 조사로는
   마땅한 게 없다고 판단했지만, 확정은 아니다).
2. 별도 Python/Node 프로세스를 **사이드카**로 띄운다. 이 사이드카가 LiveKit Agents SDK로
   room에 봇처럼 들어가서 "실시간 오디오 구독 → 되쏘기"라는 어려운 부분을 처리하고,
   캐릭터 프롬프트 조회나 메시지 저장 같은 비즈니스 로직은 새로 안 짜고 지금 있는
   Spring Boot REST API를 그대로 호출하게 한다.

2번 쪽이 훨씬 현실적이지만, 트레이드오프가 있다 — 리포에 언어/런타임이 하나 더
늘어난다는 것. 배포 파이프라인에도 그만큼 복잡도가 붙는다. 지금 이 프로젝트
스코프에서는 이 확장을 "시간이 남으면"으로 남겨두고, 대신 남은 시간을 이미 만든
기능들의 실행 검증(LiveKit/STT/TTS 자격증명 연동, 실기기 테스트)에 우선 투입하기로
했다.

## 이 결정 과정에서 남기고 싶은 것

이 프로젝트에서 정작 자랑하고 싶은 건 "WebRTC를 구현했다"는 사실 자체가 아니다.
그보다는 이 세 가지 판단이다:

1. **처음부터 리스크가 제일 큰 부분(A안)을 메인 경로에 놓지 않았다.** 실패해도
   기능이 통째로 무너지지 않도록 B안/C안으로 분리했다.
2. **중간에 새 정보(LiveKit의 WebSocket 직접 출력 옵션)를 발견했을 때, 처음 계획에
   집착하지 않고 리서치 스파이크로 먼저 검증한 뒤 계획을 갱신했다.** 이 결정 과정은
   전부 [`docs/decisions.md`](./decisions.md)의 ADR-004에 갱신 이력으로 남아있다.
3. **그럼에도 여전히 안 만든 부분(완전한 양방향 실시간)을 "몰라서 못 만든 것"이 아니라
   "일정 대비 가치를 따져서 의도적으로 남겨둔 것"으로 명시했다.** 무엇을 안 만들었는지,
   왜 안 만들었는지, 만들려면 어떤 길이 있는지까지 알고 있다는 것 자체가 이 프로젝트가
   보여주고 싶은 엔지니어링 판단력이다.

완성도를 100%로 밀어붙이는 대신, "어디까지가 이 일정에 합리적인 범위인가"를 계속
재는 것 — 그게 이 기능 하나를 통해 가장 남기고 싶었던 이야기다.
